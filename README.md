# lanpaper

**局域网轻量记事本** · 给七八个人的小组，一张共享的纸

一个只跑在局域网里的协同小工具：任务进度、经验沉淀、日常待办、最新动态。
不需要服务器、不需要账号体系、不需要联网——**电脑上有 Python 就能跑，零第三方依赖。**

<sub>MIT Licensed · Python 标准库 · 无框架无构建</sub>

## 解决什么问题

七八个人的小组，每人一台办公电脑。然后日常就会发生这种事：

- 我知道那个东西放在哪、做到哪一步了，**你不知道**
- 你电脑里记着上次那个问题最后怎么解决的，**我电脑里没有**
- 他清楚手头还剩多少，**我和你都只能靠问**
- 换到别人电脑上干活，就**看不到自己电脑里存的那堆记录**了

三个人以内，这些靠嘴说就行。七八个人就不行了——**信息压根不在一个地方，它散在七八块硬盘里。**

现成的协同工具又都太重：要么得有人搭服务器、要么要一套账号权限、要么必须联外网。
为了记几行进度，不值得。

所以缺的不是功能，是**一个大家都能看到的地方**。

## 功能

| | |
|---|---|
| **任务** | 可拆成多个阶段，点「推进」逐个完成；列表外也能一键推进 |
| **文章** | 记经验与踩坑，支持 Markdown，`Ctrl+V` 直接粘贴截图 |
| **待办** | 日常例行事项，勾一下就行；支持按每天 / 每周自动生成 |
| **动态** | 全组谁推进了什么、说了什么，一条时间线看全 |

每个动作都会留痕：

```
Lanyora 完成了 阶段[1]「前期准备」，进入 阶段[2]「方案确认」
张三     将 阶段[3]「复核」 标记为了「卡住」
李四     新建了待办「每日例行检查」
```

## 快速开始

需要 Python 3（系统自带的就够，**不需要 pip 安装任何东西**）。

```bash
python3 server/app.py
```

Windows 用 `python server/app.py`。就这一条命令，没有别的步骤。

启动后终端会打印：

```
本机访问          http://127.0.0.1:8000
局域网访问        http://192.168.1.23:8000
初始管理员邀请码   X7K2-9QMD
```

第一次注册需要那个邀请码，注册完就是管理员。之后要拉人进来：界面上点「生成邀请码」，
把码发给同事即可——**密码不用给任何人**。

把这个局域网地址发给同事，他们用浏览器打开就能用。

> 同事打不开时按顺序查：① macOS 14/15 需允许浏览器访问本地网络
> ② 首次启动的防火墙弹窗要点「允许」 ③ 确认发的是局域网地址而不是 `127.0.0.1`

## 目录结构

```
lanpaper/
├─ server/            后端（Python 标准库，无第三方依赖）
├─ web/               前端单页（原生 JS，无框架、无构建）
├─ config.json        配置
└─ data/              运行时自动创建，不用手动建
```

## 数据与备份

所有数据都在 `data/` 目录里：

| 路径 | 内容 |
|---|---|
| `data/notes.db` | SQLite 数据库（用户、任务、文章、待办、动态） |
| `data/images/` | 粘贴上传的图片，按内容哈希命名，同一张图只存一份 |
| `data/logs/` | 运行日志 |

**备份 = 拷贝整个 `data/` 目录。**
更新代码时只替换 `server/` 与 `web/`，保留 `data/`，数据不会丢。

## 配置

编辑 `config.json`：

| 项 | 说明 |
|---|---|
| `port` | 端口，默认 8000；被占用会自动往后试 |
| `initial_admin_code` | 首个管理员的邀请码。留空 = 每次启动随机生成并打印在终端 |
| `session_hours` | 登录后保持多久，默认 4 小时 |
| `max_upload_mb` | 单张图片大小上限，默认 5MB |

## 设计说明

前端界面沿用自 **[lanyora.xyz/posts](https://lanyora.xyz/posts)** 的设计——
配色、三栏布局、响应式退让规则、组件样式、背景三层叠加，都是同一套。

博客本身就是「信息流 + 侧栏 + 标签筛选」的结构，和「任务列表 + 工具面板 + 标签过滤」
几乎是一回事，所以直接搬过来用，省掉了从零设计一套视觉语言的时间
（前端从零设计视觉语言，通常比写后端还慢）。

几个设计上的取舍，都是"砍掉什么"而不是"加上什么"：

- **内容只追加，不能编辑** —— 不用做版本控制、不用处理编辑冲突，这是整个工具能保持轻量的前提
- **任务和文章同表，操作和评论同表** —— 主页信息流一条查询就出来，全文搜索只搜一处
- **只支持粘贴图片，不做文件管理** —— 一旦有了"上传文件"就要处理存储、清理、磁盘满，工具立刻变网盘
- **搜索故意没用全文索引** —— SQLite 全文索引的默认分词器不切分中文，整段中文会被当成一个词；
  换分词器又要求至少三个字符，两字词反而搜不了。直接用字符串匹配更实在

## 已知限制

- **不能存文件。** 只支持粘贴图片，没有网盘功能
- **内容不能改。** 发布即定型，只能由作者本人或管理员删除
- **没有 HTTPS。** 密码在局域网内是明文传输的，内网使用够了，别暴露到公网
- **不是给几十上百人用的。** 数据库访问是串行处理的，七八个人、十几个人没问题
- **没有任何云端同步。** 数据就在那台电脑的一个文件夹里——
  **那台电脑关了，别人就访问不了。** 这是"简单"的代价
